0. 一句话结论

飞轮转起来了，而且咬得住东西。 上游 1,886 个成品用例里选了 16 个进 L1（全绿，126 秒）；L3 黄金路径 26 步真实 HTTP 走通（6 条断言含库存账实）； 注入 3 个真实缺陷后 3 个全部被既有用例杀死；L0 抓出 4 条前端声明在后端不存在的漂移。

但同样要说清楚它做不到什么。179 条存量失败里，只有 40 条能凭“已声明并探针验证过的环境偏差”排除， 其余 139 条（77.6%）无法定责，只能进隔离区等人工签字。 这个数字不好看，但它就是本轮最重要的负面结论：一个自称能定责的分类器，在陌生仓首轮必然大面积判不出。 把它藏起来，方案就变成了演示品。

7. 失败定责：确定性分类器（LLM 不参与）

判据顺序不可逆。关键是例外表只能来自 3.env/target.yaml—— 代码里不出现任何具体包名或主机名，否则就等于给“看着像环境问题”开后门。

结论数量含义
environment_excluded40失败文本命中 target.yaml 里已声明并探针验证过的环境偏差 → 环境性排除，不计入缺陷
product_defect0改动面或增量判据成立 → 回开发，用例冻结
contract_violation0命中合同矩阵已知漂移路由 → 阻断 + 通知双方
flaky_candidate0同 commit 重跑两次均过 → 隔离区，不计入通过率但必须披露
case_stale0用例本身陈旧
unknown139五条判据均未命中 → 隔离区，必须人工签字（owner + 到期日）

两个比例，语义不同

unknown_ratio = 0.7765 —— 全量失败里的未知比例， 只用于披露存量债务质量。

new_failure_unknown_ratio = 0.0 —— 增量失败里的未知比例，才是 can-i-deploy 的实际判据。

混用这两个指标会得出相反结论：拿全量口径卡每一次部署，闸门会永久红灯； 拿增量口径去披露历史债务，债务就会消失。所以两个都算、都写进证据，用途分开。

候选集口径

候选 = l1-run-01， 新增失败 0 条。

最初实现取“最新一个 run.json”，而变异门禁每轮都落 run.json， 于是闸门会把某个变异体当候选集去判——判决对象漂移且无人察觉。现在必须显式指定。

为什么 77.6% 判不出来，这是本轮最该讲的负面结论。 分类器的每一条结论都要带可复算的证据，所以它只在两种情况下敢下判断：失败文本自己指认了缺失的前置条件（S0）， 或者改动面/基线增量能证明是候选引入（S2）。剩下的失败——比如 plugin.test_api.* 大量 404、 report.tests.TestReportTest.* 返回 None——文本里没有任何指向根因的线索。 要么补探针把根因变成可复算事实，要么让它进隔离区等签字；不能靠“我觉得是环境问题”把它划掉。 本轮选择了后者，并把这些条目连同 owner 与到期日写进台账。

8. 变异：用例到底能不能抓住缺陷

注入的不是随机翻转，是真实 PR 里出现过的写法：注释校验、去掉边界、关掉守卫。 每个变异体先 git commit 成一次真实提交（否则 git blame 看不到，S2 无法证伪），跑完立即 reset --hard。

变异体结果被杀于缺陷形态
M1-bom-self-referencekilledpart.test_bom_item.BomItemTest.test_self_reference为了让某个报错的用例先过去，直接把循环 BOM 校验注释掉。 这是"绕过校验换绿灯"的典型形态，也是自引用脏数据进入 BOM 的唯一入口。
M2-trackable-fractional-quantitykilledpart.test_bom_item.BomItemTest.test_integer_quantity去掉"可追溯件的 BOM 用量必须是整数"这一条。 线上表现：可追溯件被按 21.7 个领用，序列号无法与用量对齐， 下游工单产出与库存账永远差一个小数。
M3-order-reference-patternkilledorder.test_api.SalesOrderTest.test_so_create关掉订单编号的模式校验。这是所有单据（SO/PO/BO…）共用的唯一守卫， 一旦失效，任意字符串都能成为编号，编号前缀契约（SO-/PO-/BO-）与排序全

杀灭率 1.0（阈值 0.8），工作区还原：是。

等价变异体：一个必须留下的教训。 第一轮的 M2（放宽超分配）和 M3（短路结单守卫）都被判“存活”，看起来像断言缺口。读代码后发现是工具的问题： 放宽 SalesOrderAllocation.clean 后，同函数里 total_allocation > self.item.quantity 仍然拦截； 短路 build/models.py 的结单守卫后，build/serializers.py 的 Build order has incomplete outputs 仍然拦截。变异体没改变行为，用例当然抓不住。 把这两条当断言缺口上报，就是把工具的无能粉饰成代码的问题。所以两个锚点都重挑（可追溯件整数用量 / 单据编号模式）， 终获 3/3。

断言密度账本 5.evidence/ledger/assertion_density.csv： 2061 个用例、9391 条断言、34348 行代码，密度 0.2734； 其中 98 个用例断言行数为 0 —— 这些就是“绿灯但不可信”的候选，是唯一与通过率反向的刹车指标。

10. 环境偏差与三处不藏

  1. 数据库 sqlite3（上游 CI 用 PostgreSQL）。本机 Docker daemon 未运行。影响并发与 JSON 字段实现，不影响本次业务语义。
  2. weasyprint 声明式虚拟化。本机缺 GTK3/libgobject，而上游 report/models.py 在 import 期 sys.exit(1)，不替换则整套 Django 起不来。替身只满足导入期依赖，任何真实 PDF 渲染调用都抛 RuntimeError；受影响用例已从 L1 选择中排除并写明原因。
  3. L2 用“前后端契约矩阵”而非 Pact Broker。消费方是同仓前端，没有跨团队 broker，拉 Pact 进来是为演示而演示。 矩阵口径与 can-i-deploy 一致：消费方声明 → 提供方操作 → 是否命中。

另：L4 探索层本轮未做。方案要求“赚到资格再上”，留白比硬凑一个假 L4 诚实。
