2. 唯一真正的修改：把两端拉回同一坐标系

G1→G2 改的只有 normalize_path 里的一段：后端路径剥离 /api 前缀， 前端模板保持相对 /api。事实源（规范、前端枚举）一个字没动——这从"后端操作数、前端声明数完全不变" 可以直接证伪式的确认。改的不是数据，是坐标。

指标G1 轴错位G2 轴对齐差值说明
后端操作617617 0（不变） 同一份 openapi.yaml，事实没变
前端声明216216 0（不变） 同一份 ApiEndpoints.tsx，事实没变
命中0190 +190 只改坐标系，命中从 0 恢复为真实值
前端未命中21626 -190 从"全部未命中"收敛到 26 条真问题
后端未被引用617313 -304 304 条不是"没被用"，是"没被认出来"
为什么这一步最危险：轴错位时命中率是 0，而 0 命中的表现是"所有声明都未命中"， 看上去像"这个仓前后端对不上"这样一个业务结论，而不是"工具算错了"。 门禁此后所有基于合同矩阵的判断都会是假阴性——而且它们都会"正常"跑完。
字节级自证：G1 与 G2 的 endpoints.json 相差 2,467 字节， 而 617 条归一化路径的字符总差恰好也是 2,467 字——两者相等，说明这次修改 只删掉了 /api 前缀，没有增删任何端点、没有改任何方法或 operationId。 一个"只改坐标"的修改，应该能被字节数算出来。

4. 26 条未命中的定性：22 条体外边界，4 条真陈旧

6. 局限

  • verify-ssot 证明的是"当前 HEAD 与 SSOT 一致"，不能回溯证明某个历史提交期间的契约； 变异候选是临时提交，跑完即回滚，回滚后校验自然恢复绿。
  • G1/G2 是重放，不是原件。能保证的是"同一输入 + 同一投影逻辑 ⇒ 同一输出"， 这由 G2 与已提交产物逐字段相等来支撑。
  • 26 条未命中里"体外边界"的判定依赖前端枚举命名与模板前缀（auth/v1）， 是结构判据，不是人工豁免；新增边界必须改判据，不能改名单。
